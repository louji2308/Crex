| Command | Class | Notes |

| `pnpm --filter @crex/worker exec wrangler deploy --dry-run` | SAFE | Validates the bundle + bindings; makes no changes. **Run before every real deploy.** |

## 3. D1 binding + migrations

The D1 binding (`DB → crex`) references `migrations_dir:
../../packages/db/migrations`. The single schema source of truth is
`packages/db/migrations/*.sql`; there are **13 migrations** (`0001_init.sql` …
`0013_release_passports.sql`). `0001`–`0011` were verified applied to the remote
database on 2026-09-07; `0012_repair.sql` and `0013_release_passports.sql` are
additive files that are pending remote apply unless already applied — run
`wrangler d1 migrations list crex --remote` to confirm before shipping.

Migration command reference (the `--migrations-dir` is implied by wrangler.jsonc):

| Command | Class | Notes |
|---|---|---|
| `pnpm migrate:local` (root) = `wrangler d1 migrations apply crex --local` | SAFE | Applies pending migrations to the local `.wrangler` dev DB only. |
| `pnpm migrate:remote` (root) = `wrangler d1 migrations apply crex --remote` | SAFE **but prod-touching** | Applies *pending* additive migrations to production D1. Safe **only** when the pending set is purely additive/backward-compatible (see §11). |
| `wrangler d1 migrations list crex --remote` | SAFE | Read-only: reports applied vs pending. **Run before any remote apply.** |
| `wrangler d1 info <database_id>` | SAFE | Read-only: DB size/rows. |
| `wrangler d1 execute crex --file ...` / `--command ...` (manual SQL) | DESTRUCTIVE / AVOID | Bypasses migration bookkeeping. Any hand-run `DROP`/`DELETE` on production is unrecoverable. Do not use for schema changes. |
| `wrangler d1 delete crex` / reset | DESTRUCTIVE / AVOID | Destroys all production data. Never used. |

**Do not** edit an already-applied migration file; create the next numbered file
(`0014_*.sql`) instead.

## 10. CORS / domain config

- Worker API base URL (frontend will call): `https://crex-worker.loujanb2008.workers.dev`.
- Frontend will be served from a **different** Pages domain (e.g.
  `https://crex-web.pages.dev`) → every browser `fetch` to the worker is
  **cross-origin**, so CORS is required.
- A **minimal CORS layer was added** to the worker (`apps/worker/src/cors.ts`,
  wired into the `fetch` handler in `apps/worker/src/index.ts`):
  - Echoes `Access-Control-Allow-Origin` from the request `Origin` with
    `Vary: Origin`.
  - `OPTIONS` requests are answered with `204` + `Access-Control-Allow-Methods:
    GET, POST, OPTIONS` and `Access-Control-Allow-Headers: Content-Type`
    (JSON `POST`s preflight).
  - `Access-Control-Allow-Credentials` is **never** set: the API is public and
    credential-less, so browser cross-origin callers get the same access a `curl`
    user already has — no session/token exposure.
- Covered by `apps/worker/tests/cors.test.ts`.

If stricter origin allowlisting is ever needed, replace the echo with a checked
`ALLOWED_ORIGINS` list in `cors.ts` (no binding/var change required).

## 11. Migration process (reproducible, additive)

Local + remote procedure:

```
# 1. Add the next migration file: packages/db/migrations/0014_<name>.sql
# 2. Local (SAFE): verify against the local dev D1
pnpm migrate:local            # wrangler d1 migrations apply crex --local
# 3. Diff/pending check (SAFE, read-only):
npx wrangler d1 migrations list crex --remote          # confirm the pending set (0012/0013 unless already applied)
# 4. Production (SAFE only if step 3 shows an additive pending set):
pnpm migrate:remote           # wrangler d1 migrations apply crex --remote
# 5. Verify (SAFE):
npx wrangler d1 migrations list crex --remote          # "No migrations to apply!"
```

All existing migrations are additive (`CREATE TABLE`/`ALTER TABLE ADD COLUMN` /
indexes + seeds), so the set is forward/backward compatible: an older worker bin
runs fine against the newer schema (new columns are optional/NULLable by design).

## 12. Rollback considerations

**Worker rollback (safe, versioned):**

- After a bad deploy, list versions:
  `npx wrangler versions list` (or the dashboard **Deployments** tab). SAFE.
- Roll back:
  - `npx wrangler rollback` — immediately restores the **previous** version, or
  - `npx wrangler rollback <version-id>` — restores a specific version, or
  - update the **tag** to promote a known-good version:
    `npx wrangler versions upload --tag <new>/<version-id>`; then set the
    production tag: `npx wrangler tags update <new> --tag current/blue/green`.
- Because each deployed version is immutable and preserved, rollback is
  instantaneous and does not rebuild.

**D1 migration rollback:**

There is **no destructive rollback**. The strategy is **additive forward
migrations**: never delete production rows/columns; to undo an unwanted migration,
write a new forward migration (`0014_*`) that reverts the data change (e.g. backfill
values) rather than dropping anything. `workflow_state`, `source_assets`,
`ai_outputs`, etc. are all append/update tables — a mistaken state transition is
repaired with a corrective update, not a table reset.

**R2 rollback:** object keys are namespaced and immutable-in-place; a mistaken
overwrite is recovered from the source object + re-upload, not a bucket reset.
